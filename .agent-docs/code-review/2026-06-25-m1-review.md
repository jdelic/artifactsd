## Architecture assessment — sound

- **Layering matches the design.** The package layout proposed in
  `design/01-architecture.md §4` is implemented as written. `internal/` keeps the
  surface private; `pkg/apiclient` is the single importable client.
- **`pkg/apiclient` is genuinely the only HTTP client.** Verified zero
  `http.NewRequest` / `http.Client{}` / `http.Get|Post` constructions in `cmd/`
  or `internal/mcp` (outside tests). Both `artifactctl` and the MCP adapter route
  every call through `apiclient`, exactly as `design/01 §4` intends ("the CLI and
  MCP adapter never duplicate request logic"). This is the highest-value
  anti-duplication property in the repo and it holds.
- **The security decision path is centralized in `internal/policy`.**
  `policy.Decide` is the one place that encodes existence-non-disclosure
  (private/expired/bearer-hidden/listing-off → 404) and challenge precedence
  (oidc → basic → bearer, `design/03 §5`). Serve handlers do not re-implement any
  of it. `compileVerifiers` is the single bridge from `meta.AuthEntry` to
  `auth.Verifier`. This is exactly where you want zero duplication.
- **The management API is well-factored.** Shared helpers
  (`lookupCollection`, `resolveFile`, `lookupShare`, `lookupUploadSession`,
  `prepareMetadata`/`mergeMetadata`, `writeError`/`internalServerError`) mean the
  handlers don't repeat resolution or error-envelope logic within the package.
- **Metadata engine separation is clean.** `meta.Resolve` (inheritance chain →
  `Effective`) and `meta.Merge` (patch → `Document`) are deliberately distinct
  shapes; they look similar but serve different callers and are correctly *not*
  merged into one function.

## Abstractions — no concerns

The pointer-vs-value modelling in `meta.Document` (optional sections via
pointers; `Access.Auth` as `*[]AuthEntry` so "unset/inherit" is distinguishable
from "explicit empty / no auth") is the right call and is used consistently by
both `Resolve` and `Merge`. The `blob` package hides storage behind an interface
per `design/01 §8`, keeping a future S3 move possible.

## Improvement made in this review

**Added `internal/meta/merge_test.go` (7 tests).** `meta.Merge` backs every
`PATCH .../meta` route (collections, folders, files, shares) and has subtle
semantics — header empty-value removal, `access.auth` wholesale-replace vs.
unset-preserve, scalar override, nil-base-section creation. It had **no direct
unit test** in its own package; it was only exercised incidentally through API
integration tests. The new tests lock the `design/03 §2` semantics. Direct
coverage of `Merge` went 0% → **92.5%**; `internal/meta` self-coverage rose to
89.5%. All quality gates still pass.

## Findings (filed as M2 tickets under epic `artifactsd-lw4`)

### Finding 1 — `meta.Merge` header-key canonicalization inconsistency
**Ticket: `artifactsd-lw4.1` (bug, P3, area:meta)**

`meta.Resolve.apply` canonicalizes header keys via `http.CanonicalHeaderKey`
(`internal/meta/resolve.go:64`), but `meta.Merge` matches and deletes on the
**raw** JSON key (`internal/meta/merge.go:19-27`). Consequences:

- A `PATCH .../meta` that deletes `content-type` (empty value) when the stored
  document holds `Content-Type` silently no-ops — the delete doesn't match.
- A case-variant override can leave two map entries (`Content-Type` and
  `content-type`) that only collide *after* `Resolve` canonicalizes them; since
  `apply` iterates the map in random order, which value wins is non-deterministic.

Stored documents keep raw keys today and `Resolve` canonicalizes at serve time,
so the common single-case path is correct — this is a latent edge case, not an M1
regression. Preferred fix is to canonicalize header keys at **write/validate
time** so stored documents are canonical end-to-end (also removes the random-
iteration collision in `Resolve`). See ticket for the decision and acceptance
criteria.

### Finding 2 — `resolveShareTarget` duplicated across `api` and `admin`
**Ticket: `artifactsd-lw4.2` (chore, P4, area:api)**

`internal/api/shares.go:168` and `internal/admin/shares.go:157` each implement
`resolveShareTarget` with identical core logic (empty path → `"collection"`; else
clean path + `store.GetNode` → `node.Kind`), differing only in error convention
(api writes HTTP responses and returns `ok bool`; admin returns an `error`).
~12 lines duplicated across the api/admin package boundary. This is the **only**
genuine logic duplication found. Extraction needs a shared not-found sentinel so
callers can map to 404 vs 500 — flagged as a judgment call because the
abstraction cost may exceed the benefit for 12 lines.

### Finding 3 — Direct unit-test coverage for core engine functions
**Ticket: `artifactsd-lw4.3` (task, P4, area:store)**

Beyond `meta.Merge` (fixed this review), several core functions have 0% *direct*
(self-package) coverage and are only exercised through integration tests, so
their semantics aren't locked at the unit level — notably the janitor query layer
in `internal/store/expiry.go` (`ListExpiredNodes`, `ListExpiredCollections`,
`ListExpiredShares`, `NodeBlobRefs`, `BlobRefCount`) and the ID generators in
`internal/auth/token.go` (`GenerateShareID`, `GenerateUploadID`). The
shared-blob ref-count boundary (a blob is deleted only when its *last*
referencing node expires) is the highest-value case to lock directly.

## Things deliberately NOT changed

- **`internal/upload` is an empty stub** (package decl + doc comment only). Upload
  lifecycle actually lives in `internal/store/uploads.go`, `internal/api/uploads.go`,
  and `internal/admin/uploads.go`. This lines up with the open M2 epic
  `artifactsd-90i` (resumable/chunked uploads, decision F2), so it reads as a
  deliberate placeholder. Left as-is; revisit when `artifactsd-90i` lands (either
  fill it or fold the upload code into it).
- **Admin error pattern repetition.** ~23 occurrences of
  `http.Error(w, "loading …: "+err.Error(), 500)` in `internal/admin`. Consistent
  and idiomatic; wrapping in a helper would add indirection for no real gain.
- **Two init-time `panic`s** (`internal/server/admin.go:39` session-key
  generation, `internal/admin/assets.go:16` embedded-asset load). Both are
  fail-fast at process start on conditions that cannot occur in a correct build;
  appropriate use of panic.
- **`meta.Resolve` vs `meta.Merge` similarity.** Intentionally separate (different
  output types and callers); not duplication.

## Newly-landed code reviewed this pass

### `artifactctl skill install <agent>` (artifactsd-hp9, `cmd/artifactctl/skill.go`)

Landed on `main` between the first review pass and this one; reviewed here so the
next agent doesn't need to re-cover it. **Assessment: clean, well-tested, no
issues filed.**

- The root-level `package artifactsd` (`skill.go` + `skill_test.go`) exists solely
  to `go:embed SKILL.md`, which must live at or below the embedding package —
  `cmd/artifactctl` can't reach the repo-root file. A thin root package is the
  standard Go workaround and is the right call.
- `skillTargets` is a clean data-driven table (agent → mode + local/global path);
  adding an agent is a one-entry change. The two install modes (verbatim copy vs.
  marker-delimited merge) are well separated.
- `mergeSkillBlock` is idempotent and defensive: it replaces only the
  marker-delimited block, preserves surrounding content, creates the file if
  absent, and errors clearly on a start-marker-without-end-marker. Good.
- `copilot --global` correctly errors (no established user-wide location);
  `resolvePath` handles an unset `$HOME`.
- 10 test functions in `skill_test.go` cover copy, merge, idempotent re-run,
  unknown agent, and the `--global`/copilot edge cases. Coverage is adequate; no
  additional tests warranted.

Minor, non-blocking observation (not ticketed): the two install file-writes use
`0o644` with `//nolint:gosec`, while parent dirs use `0o750`. This is consistent
and justified (agent tooling expects world-readable instruction files), just
noted for awareness.
